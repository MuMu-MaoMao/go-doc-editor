# 01 · 总体原则

> 本文档定义了 go-doc-editor 项目的**核心理念和基本原则**。
> 所有贡献者在着手开发前应首先理解这些原则。

---

## 1.1 核心信条

| 原则 | 说明 |
|------|------|
| **约定优于配置** | 遵循 Go 社区和本规范的约定，减少决策成本 |
| **渐进设计** | 架构随项目成长而演进，拒绝过度设计 |
| **契约优先** | 接口先行（handler → service → model），实现随后 |
| **文档即代码** | 文档与代码同源、同版本、同审查 |
| **安全内置** | 安全不是后加的特性，而是设计的固有部分 |

## 1.2 架构风格

本项目选用 **分层架构（Layered Architecture）+ 后端代理模式**：

```
前端 (static/) → Handler (HTTP 适配) → Service (业务逻辑) → 外部资源 (文件系统/API)
```

关键约束：
- **依赖方向始终向内**：Handler → Service → Model/外部资源
- **各层通过结构体依赖注入**连接（而非全局变量或单例）
- **数据流单向**：请求 → Handler → Service → 响应

## 1.3 设计决策原则

| 场景 | 原则 |
|------|------|
| 新增依赖 | 先问自己："这个依赖真的必要吗？标准库能否实现？" |
| 选择方案 | 简单方案优先，复杂方案仅在证据充分时采用 |
| 异常处理 | 尽早失败（fail fast），错误信息要可追溯 |
| 性能优化 | 先有数据（profile），后优化；不做无依据的优化 |
| 安全考量 | 每个输入都是不可信的，每个外部调用都要有超时 |

## 1.4 与现有 README 的关系

`readme.md` 是项目的**技术概览**（架构、API、如何运行），
本文档及系列文档是**开发规范**（怎么写代码、如何协作）。

两者互补：开发时参考规范文档，对外介绍时使用 readme。
