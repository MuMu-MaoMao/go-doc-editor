# 03 · 提交信息规范

> go-doc-editor 采用 **Conventional Commits** 规范管理提交信息。
> 每次 `git commit` 时请参考本文档。

---

## 3.1 格式

```
<type>(<scope>): <description>

[optional body]

[optional footer(s)]
```

## 3.2 提交类型

| 类型 | 在项目中的含义 | 示例 |
|------|---------------|------|
| `feat` | 新功能（新 handler、新 service 方法、新前端页面） | `feat(handler): add file rename endpoint` |
| `fix` | 修复 Bug | `fix(service): correct path traversal check on Windows` |
| `docs` | 仅文档变更 | `docs: update API endpoint list in readme` |
| `style` | 代码格式化（无功能变化） | `style: run gofmt on all files` |
| `refactor` | 代码重构（不改变外部行为） | `refactor(ai): extract SSE writer to separate helper` |
| `test` | 新增或修改测试 | `test(service): add table-driven tests for safeFilePath` |
| `chore` | 构建、依赖、CI 配置 | `chore(deps): bump golang-jwt to v5.2.2` |
| `perf` | 性能优化 | `perf(static): add cache headers for static assets` |
| `ci` | CI 配置变更 | `ci: add lint check to GitHub Actions` |

### 何时使用 breaking change

如果变更破坏了向后兼容性（如重命名 API 端点、修改请求/响应结构），
在类型后加 `!` 或在 footer 中添加 `BREAKING CHANGE:`：

```
feat(handler)!: merge register and login into single auth endpoint

BREAKING CHANGE: /api/register and /api/login are replaced by /api/auth
```

## 3.3 scope（可选范围）

scope 标明变更影响的模块，建议使用以下值：

| Scope | 对应模块 |
|-------|---------|
| `handler` | HTTP 处理器层 |
| `service` | 业务逻辑层 |
| `auth` | JWT 认证模块 |
| `model` | 数据模型/DTO |
| `middleware` | HTTP 中间件 |
| `config` | 配置模块 |
| `user` | 用户存储 |
| `static` | 前端静态文件 |
| `deps` | 依赖变更 |

## 3.4 好的提交示例

```
feat(handler): add file rename API endpoint

Implements PUT /api/file/{filename}/rename for renaming documents.
Adds RenameFile method to FileService with safety validation.

Closes #42
```

```
fix(service): correct path traversal check on Windows

On Windows, filepath.Abs("C:\foo") returns "C:\foo" without a trailing
separator, causing the prefix check to fail for the user's own directory.

Fixes #38
```

```
docs: add development workflow documentation

Adds DEVELOPMENT_WORKFLOW.md with branching strategy, commit conventions,
code style, architecture standards and testing requirements.
```

## 3.5 提交检查清单

在 `git commit` 前快速对照：

- [ ] 类型正确（`feat`/`fix`/`docs`/`refactor`/`test`/`chore`/`perf`/`ci`）
- [ ] scope 可选，在括号内
- [ ] 描述用**祈使语气**（"add" 而非 "added" 或 "adds"）
- [ ] 首行不超过 **72 个字符**
- [ ] 类型后冒号后**小写**开头（`feat: add` 而非 `feat: Add`）
- [ ] 末尾**不加句号**
- [ ] 正文说明"**为什么**"和"**怎么做**"
- [ ] 关联 issue 用 `Closes #N` / `Fixes #N`

## 3.6 何时 squash 提交

PR 中的审查反馈修复应 squash 后再合并，保持 main 历史的整洁。

推荐策略：**在 GitHub 上使用 "Squash and merge"**，将整个 PR 压缩成一个符合 Conventional Commits 格式的提交。
