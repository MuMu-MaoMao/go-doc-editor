# 07 · 代码审查流程

> 本文档定义 go-doc-editor 的 Pull Request 创建规范和代码审查标准。
> **提交 PR 或审查他人代码时**请参考本文档。

---

## 7.1 PR 创建规范

### 7.1.1 PR 模板

```markdown
## 描述

[简述变更内容和动机]

## 类型

- [ ] 功能 (feat)
- [ ] 修复 (fix)
- [ ] 重构 (refactor)
- [ ] 文档 (docs)
- [ ] 测试 (test)
- [ ] 杂项 (chore)

## 检查清单

- [ ] 代码通过 `go vet ./...`
- [ ] 代码通过 `gofmt`
- [ ] 导出符号有注释
- [ ] 错误被正确处理（未忽略）
- [ ] 新功能包含测试
- [ ] API 变更已更新到 readme.md
- [ ] ADR 已创建（如适用）

Closes #N
```

### 7.1.2 PR 大小规范

| 标准 | 要求 |
|------|------|
| **单次变更** | 一个 PR 只做**一件事** |
| **文件数** | 不超过 15 个（建议 3-8 个） |
| **代码行数** | 不超过 500 行（排除测试和自动生成代码） |
| **审查时间** | 目标 20 分钟内完成一次审查 |

### 7.1.3 PR 标题格式

PR 标题必须符合 Conventional Commits 格式，合并时作为 commit message：

```
feat(handler): add file rename endpoint
fix(service): correct path traversal check on Windows
docs: update development workflow documentation
```

## 7.2 Go 代码审查检查清单

### 错误处理
- [ ] 错误使用 `fmt.Errorf("...: %w", err)` 包装，而非 `fmt.Sprintf`
- [ ] 没有使用 `_` 忽略错误
- [ ] `defer` 在错误检查前正确使用
- [ ] 资源（文件句柄、HTTP 连接）有 `defer` 释放

### 并发安全
- [ ] 共享状态使用 `sync.RWMutex` 保护
- [ ] goroutine 生命周期可追踪，无泄漏
- [ ] 使用 `sync.WaitGroup` 等待 goroutine 完成

### 安全
- [ ] 路径操作通过 `safeFilePath()` 校验
- [ ] JWT 验证使用正确的签名方法（HS256）
- [ ] 密码使用 bcrypt 加密（`golang.org/x/crypto/bcrypt`）

### 性能
- [ ] 避免不必要的内存分配（如预分配 slice）
- [ ] JSON 序列化使用 `json.NewEncoder` 而非多次 `json.Marshal`
- [ ] 大文件流式处理而非一次性读入内存

### Go 惯例
- [ ] `context.Context` 作为函数第一个参数
- [ ] 接口定义在消费者侧
- [ ] 包名小写单数

## 7.3 前端审查检查清单

- [ ] Token 安全：前端不保存 API key
- [ ] XSS 防护：用户内容经过 DOMPurify 渲染
- [ ] 网络错误在 UI 上有反馈（状态提示、错误消息）
- [ ] SSE 的 `ReadableStream` 读取正确，buffer 拼接无误
- [ ] 移动端响应式正常

## 7.4 合并条件

PR 必须满足以下**所有**条件才能合并：

- [ ] **至少 1 人 Code Review 通过**（单人项目可放宽，但仍需自我逐项检查）
- [ ] **CI 检查全部通过**（测试、lint、build）
- [ ] **无未解决的讨论线程**
- [ ] **PR 标题符合 Conventional Commits 格式**

## 7.5 单人项目的自我审查建议

即使是单人开发，建议在合并 PR 前：

1. **休息 15 分钟**后重新看自己的 diff，以"陌生视角"审视
2. **逐行运行**上述 Go 审查检查清单
3. **运行完整测试**：`go test ./... -race`
4. **对照文档**检查是否需要更新 README 或 ADR
