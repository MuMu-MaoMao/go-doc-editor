## 8.1 核心理念：三重测试架构

一次完整的功能验证应经过**三个独立视角**的检验，每个视角覆盖不同的盲区：

```
┌──────────────────────────────────────────────────────────────────┐
│                      三重测试架构                                  │
│                                                                  │
│  第一层：脚本测试（Script Testing）                                │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  curl / Go test / Python 脚本                             │    │
│  │  覆盖：API 正确性、边界条件、用户隔离、错误处理             │    │
│  │  特点：可重复、自动化、快速反馈                              │    │
│  │  工具：curl、go test、httptest、shell 脚本                  │    │
│  └──────────────────────────────────────────────────────────┘    │
│                            ↓                                     │
│  第二层：Claude 浏览器测试（AI Browser Testing）                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  Claude 通过浏览器直接操作 UI                              │    │
│  │  覆盖：前后端联调、UI 交互、多步骤流程                      │    │
│  │  特点：模拟真实用户操作路径，发现 API 正确但 UI 错误的场景    │    │
│  │  工具：Claude in Chrome 扩展                               │    │
│  └──────────────────────────────────────────────────────────┘    │
│                            ↓                                     │
│  第三层：用户验收测试（User Acceptance Testing）                   │
│  ┌──────────────────────────────────────────────────────────┐    │
│  │  用户亲自在浏览器中操作                                    │    │
│  │  覆盖：体验感受、视觉合理性、是否符合预期                    │    │
│  │  特点：最终裁判，发现自动化测试无法捕捉的"违和感"            │    │
│  └──────────────────────────────────────────────────────────┘    │
│                                                                  │
│  层级递进：下层验证通过 → 进入上层                                │
│  跳过规则：不是每次都需三层全跑，见 **三重测试选择矩阵**           │
└──────────────────────────────────────────────────────────────────┘
```

### 为什么需要三层

| 测试层 | 能发现 | 不能发现 |
|--------|--------|---------|
| 脚本测试 | API 返回 500、JSON 格式错误、数据不一致 | UI 样式错乱、登录按钮不可用 |
| Claude 浏览器测试 | 页面空白、JS 报错、操作流程不通 | 字体大小是否舒适、配色是否顺眼 |
| 用户验收测试 | 功能不好用、交互不自然、不符合直觉 | 后端数据一致性（用户看不到 SQL） |

三层互补，缺一层就可能让 Bug 溜到生产环境。

## 8.2 三重测试选择矩阵

不是每个功能都需要跑满三层。根据功能类型和改动范围选择：

| 功能类型 | 脚本测试 | Claude 浏览器测试 | 用户验收测试 | 说明 |
|---------|:-------:|:----------------:|:-----------:|------|
| **后端 API 新增/修改** | ✅ 必须 | ⚠️ 按需 | ⚠️ 按需 | API 格式正确性由脚本保障，UI 无关可不跑上层 |
| **前端 UI 修改** | ⚠️ 按需 | ✅ 必须 | ✅ 必须 | 样式改动用脚本测意义不大，重点是人眼判断 |
| **全栈功能（前后端+数据）** | ✅ 必须 | ✅ 必须 | ✅ 必须 | 三层全跑，任何一层遗漏都有风险 |
| **纯配置/环境变更** | ✅ 必须 | ❌ 跳过 | ❌ 跳过 | 改个端口号用 curl 确认即可 |
| **修复 Bug** | ✅ 必须 | ⚠️ 按需 | ⚠️ 按需 | 先写重现脚本，修好后脚本通过即基本可信 |
| **实验性功能（范式 C）** | ✅ 必须 | ❌ 跳过 | ❌ 跳过 | 快速验证可行性，不投入上层测试精力 |

### 在范式 A/B/C 中的应用

| 范式 | 测试策略 | 说明 |
|------|---------|------|
| **范式 A**（完整规格） | **三层全跑** | 在 Step 5（增量实现）中写脚本测试，在 Step 7（验收测试）中执行 Claude 测试和用户测试 |
| **范式 B**（轻量迭代） | **脚本测试 + 用户验收** | 跳过 Claude 浏览器测试层，减少沟通开销 |
| **范式 C**（实验探索） | **仅脚本测试** | 快速验证假设，不投入 UI 级测试精力 |

## 8.3 第一层：脚本测试（Script Testing）

### 8.3.1 测试脚本文件规范

测试脚本存放在 `scripts/test/` 目录下，按功能模块组织：

```
scripts/test/
├── api/                      # API 接口测试脚本
│   ├── test-auth.sh          # 注册/登录测试
│   ├── test-docs.sh          # 文档 CRUD 测试
│   ├── test-docs.bat         # Windows 批处理版本
│   ├── test-ai.sh            # AI 对话测试
│   └── test-isolation.sh     # 用户隔离测试
├── unit/                     # Go 单元测试（沿用标准 _test.go）
│   ├── ...
└── utils.sh                  # 通用工具函数（JWT 解析、JSON 提取等）
```

### 8.3.2 脚本测试编写规范

每条测试脚本应包含：

```bash
#!/bin/bash
# =============================================
# 测试套件：文档 CRUD
# 测试范围：ListFiles / ReadFile / SaveFile / DeleteFile
# 关联功能：文档数据库存储（2026-06-06）
# 前置条件：服务已运行在 localhost:3000
# =============================================

BASE_URL="http://localhost:3000"
PASS=0
FAIL=0

# 辅助函数
check() {
    local desc="$1"
    local expected="$2"
    local actual="$3"
    if echo "$actual" | grep -q "$expected"; then
        echo "  ✅ $desc"
        PASS=$((PASS + 1))
    else
        echo "  ❌ $desc (期望含: $expected, 实际: $actual)"
        FAIL=$((FAIL + 1))
    fi
}

# 1. 注册
echo "=== 注册 ==="
RESP=$(curl -s -X POST "$BASE_URL/api/register" \
  -H "Content-Type: application/json" \
  -d '{"username":"testuser","password":"test123"}')
check "注册新用户" "success" "$RESP"

# 2. 登录
echo "=== 登录 ==="
RESP=$(curl -s -X POST "$BASE_URL/api/login" \
  -H "Content-Type: application/json" \
  -d '{"username":"testuser","password":"test123"}')
TOKEN=$(echo "$RESP" | python3 -c "import sys,json;print(json.load(sys.stdin).get('token',''))")
check "登录获取 Token" "token" "$RESP"

# 更多测试...

echo ""
echo "结果: $PASS 通过, $FAIL 失败"
```

### 8.3.3 测试脚本的关键设计原则

1. **幂等性**：每次运行前清理测试数据，不依赖上次运行状态
2. **独立性**：每条测试可独立运行，不依赖其他测试的执行顺序
3. **自验证**：每个测试步骤自动判断 pass/fail，不需要人工看输出
4. **可重复**：同一脚本反复运行结果一致
5. **可追溯**：失败时输出足够的上下文信息以便排查

### 8.3.4 Go 单元测试（沿用）

Go 标准 `_test.go` 测试保持原有规范不变：

| 层级 | 方式 | 说明 |
|------|------|------|
| Service 单元测试 | `go test` + `httptest` | 表驱动测试，覆盖核心逻辑 |
| Handler 集成测试 | `go test` + `httptest` | 模拟 HTTP 请求，验证响应 |
| 端到端脚本测试 | curl shell 脚本 | 模拟真实 API 调用，验证完整链路 |

## 8.4 第二层：Claude 浏览器测试

### 8.4.1 适用条件

- Claude in Chrome 扩展已连接
- 待测功能涉及 UI 交互（点击、输入、页面跳转）
- 需要验证前后端联调是否正常

### 8.4.2 测试流程

1. 开发者启动本地服务
2. Claude 通过浏览器扩展打开 `http://localhost:3000`
3. Claude 模拟用户操作：注册 → 登录 → 新建 → 编辑 → 删除
4. Claude 同时观察页面变化和后端响应
5. 记录测试结果到验收报告

### 8.4.3 测试重点

- 页面是否正常加载（无白屏、无 JS 错误）
- 操作流程是否通顺（点击跳转、提交反馈）
- 前后端数据是否一致（保存后刷新页面，数据仍在）
- 错误状态是否有 UI 反馈（如 401 跳转登录）

## 8.5 第三层：用户验收测试

### 8.5.1 什么时候需要用户参与

| 场景 | 必须用户测试 | 可以跳过 |
|------|:----------:|:--------:|
| UI 布局/样式修改 | ✅ | |
| 新增操作流程（如拖拽、右键菜单） | ✅ | |
| 纯后端 API 变更（接口格式不变） | | ✅ |
| Bug 修复（已有脚本覆盖） | | ✅ |
| 性能/体验相关改动 | ✅ | |

### 8.5.2 用户测试流程

1. Claude 或开发者提供**测试清单**（checklist），列出每一步操作和预期结果
2. 用户按清单操作，逐项打勾
3. 记录发现问题
4. 用户给出**最终评价**

### 8.5.3 用户测试清单模板

```markdown
## 验收测试清单

| # | 测试步骤 | 预期结果 | 实际结果 | 状态 |
|---|---------|---------|---------|:----:|
| 1 | 打开首页 `http://localhost:3000` | 页面正常加载 | | |
| 2 | 注册新账号 | 提示注册成功 | | |
| 3 | 登录 | 跳转到编辑器 | | |
| 4 | 新建文件 test.md | 文件出现在列表中 | | |
| 5 | 写入内容并保存 | 提示保存成功 | | |
| 6 | 关闭后重新打开 | 内容仍在 | | |
| 7 | 删除文件 | 文件从列表中消失 | | |
| 8 | 用另一个账号登录 | 看不到此文件 | | |

**发现问题**：...

**总体评价**：[适合当前功能 / 需要改进 / 不通过]
```

## 8.7 测试脚本目录规划

```
scripts/
└── test/
    ├── api/                      # 脚本测试（curl，按功能模块分文件）
    │   ├── test-auth.sh          # 注册/登录
    │   ├── test-docs.sh          # 文档 CRUD（参照 8.6 范例）
    │   ├── test-isolation.sh     # 用户隔离
    │   └── test-ai.sh            # AI 对话
    ├── unit/                     # Go 单元测试（_test.go，在源码同目录下）
    └── utils.sh                  # 公共工具函数
```

### 脚本文件命名规范

```
test-<模块名>.sh      # Linux/macOS
test-<模块名>.bat     # Windows
```

### 脚本的 "四性" 检查清单

- [ ] **幂等性**：运行前清理测试数据，重复运行结果一致
- [ ] **独立性**：不依赖其他脚本的执行顺序
- [ ] **自验证**：自动判断 pass/fail，无需人工看输出
- [ ] **可追溯**：失败时输出请求 URL、响应体和期望值

## 8.8 测试运行命令

```bash
# 运行所有 Go 单元测试
go test ./... -v

go test ./... -race

go test ./... -coverprofile=coverage.out

# 运行 API 脚本测试
bash scripts/test/api/test-docs.sh

# 运行全部 API 测试套件
for f in scripts/test/api/*.sh; do echo "=== $f ==="; bash "$f"; done
```

## 8.9 三重测试与现有流程的融合

### 范式 A（Step 5 增量实现）

```
实现代码 → 写测试脚本（scripts/test/api/）
        → 运行脚本验证 → 通过后提交
        → Step 7 验收时：Claude 测试 + 用户测试
```

### 范式 B

```
实现代码 → 运行脚本测试（已有脚本）
        → 用户验收（省略 Claude 测试层）
```

### 范式 C

```
快速实现 → 运行最小脚本验证可行性
        → 跳过 UI 测试层
```

> **核心原则**：脚本测试是底线，任何时候不能跳过。
> Claude 浏览器测试和用户验收测试根据改动范围和范式类型按需选择。
