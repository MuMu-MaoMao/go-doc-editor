# 12 · 功能开发流程规范（Feature Development Workflow）

> 本文档定义从**提出需求**到**功能完善**的完整开发流程。
> 每次启动新功能开发时，根据功能规模选择对应的流程范式，
> 并按步骤执行、记录日志。

## 适用场景速查

| 你的情况 | 推荐范式 |
|---------|---------|
| 需求明确，改动涉及多层（前端+后端+数据） | **范式 A** |
| 需求简单或模糊，边做边明确 | **范式 B** |
| 全新的技术方向，不确定能否实现 | **范式 C** |
| 修复一个 Bug | 范式 B（跳过规划，直接测试验证） |
| 重构已有功能（不改变外部行为） | 范式 B |
| 集成外部 API（如换 AI 模型） | 范式 A |

---

## 通用原则

无论选择哪种流程，以下原则贯穿始终：

### 1. 单次只做一件事

一个功能分支只做一个功能。如果发现额外问题，记下来另开分支。

### 2. 先写文档，后写代码

| 阶段 | 先产出 | 再动手 |
|------|-------|-------|
| 提出想法 | 写需求草案 / log | 开始开发 |
| 确定方案 | 写规格说明 / 方案对比 | 实现 |
| 发现 Bug | 写重现测试 | 修复 |

### 3. 每一步都要留 Log

每个步骤完成后，在 `docs/logs/` 下留下一份**日期标注的日志文档**，
格式见[Log 日志规范](#log-日志规范)章节。

### 4. 每步有 Checkpoint

每一步完成时都要确认：
- 当前阶段的目标是否已完成？
- 是否可进入下一步？
- 是否需要外部确认（向负责人展示、讨论）？

## 范式 A：完整规格驱动（Spec-Driven）

> **适用场景**：需求明确、涉及多层改动（后端的 service/handler 修改 + 前端 UI + 可能涉及数据模型变更）。
> 典型例子：新增一个功能模块、集成外部 API、引入新设计模式。

### 流程总览

```
[1] 需求提出       → [2] 编写 Spec    → [3] 技术方案设计  → [4] 任务拆解
                                                              │
                                                              ▼
                                                      [5] 增量实现 + 测试
                                                              │
                                                              ▼
                                              [6] Code Review → [7] 用户测试
                                                                    │
                                                                    ▼
                                             [8] 反馈迭代（循环回到 2 或 5 或 6）
```

---

### 第 1 步：需求提出

**做什么**：明确"要做什么"和"为什么做"。用自然语言描述功能，
不要涉及技术实现细节。

**产出文档**：`docs/logs/YYYY-MM-DD-feat-<名>-需求.md`

**检查清单**：
- [ ] 目标用户是谁？
- [ ] 这个功能解决什么问题？
- [ ] 不做的代价是什么？
- [ ] 初步接受标准（怎么算"做好了"）？
- [ ] 是否有依赖项（需要其他人或其他功能先完成）？

**Log 模板**：

```markdown
# 功能需求 Log

- **日期**: 2026-06-06
- **提出人**: [姓名]
- **功能名称**: AI 角色扮演
- **当前阶段**: 需求提出 ✅

## 功能描述
[用自然语言描述功能。]

## 动机与目标
- 解决什么问题：...
- 目标用户：...

## 初步接受标准
- [ ] ...
- [ ] ...

## 备注
[前置依赖、注意事项等]
```

---

### 第 2 步：编写 Spec（规格说明）

**做什么**：将需求转化为具体的功能规格说明，包括功能边界、
用户交互流程、数据格式等。

**产出文档**：`docs/specs/<功能名>-spec.md`

**检查清单**：
- [ ] Spec 包含六个核心区域：目标、项目结构、代码风格、测试策略、边界条件、成功标准
- [ ] 成功标准是可测试的（具体、可验证）
- [ ] 边界已定义：Always / Ask First / Never
- [ ] 有 1-2 个替代方案（如果适用）
- [ ] 有开放问题列表（尚未确定的决策）

**Log**：更新到 `docs/logs/YYYY-MM-DD-feat-<名>-需求.md`，追加"编写 Spec"章节。

---

### 第 3 步：技术方案设计

**做什么**：确定具体的技术实现方案。包括：
- 需要修改哪些文件（文件清单）
- 架构变更（新增模块、拆分/合并文件）
- 数据流（数据怎么走）
- 安全考虑（认证、权限、输入校验）
- 列出 2-3 种技术方案并对比，说明选中方案的理由

**产出文档**：`docs/specs/<功能名>-tech-design.md`

**检查清单**：
- [ ] 列出所有受影响的文件（变动清单）
- [ ] 数据流图或调用链路
- [ ] 至少对比 2 种方案（A：... B：... C：...）
- [ ] 安全审计点已标注
- [ ] 兼容性检查（向后兼容？）

**Log**：更新到 `docs/logs/YYYY-MM-DD-feat-<名>-需求.md`，追加"技术方案"章节。

---

### 第 4 步：任务拆解

**做什么**：将设计拆分为可独立完成的小任务。每个任务：
- 可在一次开发会话中完成（建议 30-60 分钟）
- 有明确的接受标准
- 有验证步骤（测试命令 / 手动检查方法）
- 标注了前后依赖关系

**产出文档**：`docs/specs/<功能名>-tasks.md`

**任务模板**：

```markdown
## Task N: [任务名]

**描述**：[一句话说明]

**接受标准**：
- [ ] [具体条件]

**验证方式**：
- [ ] 运行测试：`go test ./internal/service/ -run TestXxx`
- [ ] 手动检查：[具体步骤]

**依赖**：依赖 Task [M]
**涉及文件**：
- `cmd/server/main.go`
- `internal/service/xxx.go`
```

**Log**：更新到 `docs/logs/YYYY-MM-DD-feat-<名>-需求.md`，追加"任务拆解"章节。

---

### 第 5 步：增量实现 + 测试

**做什么**：按 Task 顺序逐一实现，每次只做一件事，做完就测试。

实现时遵循 **增量实现** 原则：
1. 实现最小的完整功能片段
2. 运行测试（`go test ./...`）
3. 验证功能正常
4. 提交 commit（信息遵循 `03-提交信息规范.md`）
5. 进入下一个 Task

**产出**：功能代码 + 测试代码 + commit

**检查清单**（每个 Task 完成后）：
- [ ] 新增代码通过 `go vet ./...`
- [ ] 相关测试通过
- [ ] 完整测试套件通过（`go test ./... -race`）
- [ ] 构建成功
- [ ] Commit 信息符合规范
- [ ] 该 Task 的接受标准已满足

**Log**：更新到 `docs/logs/YYYY-MM-DD-feat-<名>-实现日志.md`

---

### 第 6 步：Code Review（自我审查）

**做什么**：代码完成后，对照 `07-代码审查流程.md` 做审查，
写下审查记录。

**产出文档**：`docs/logs/YYYY-MM-DD-feat-<名>-审查记录.md`

**检查清单**：
- [ ] 对照"Go 代码审查检查清单"逐项检查
- [ ] 对照"前端审查检查清单"逐项检查
- [ ] 审查发现的问题已修复或记录为后续任务

---

### 第 7 步：用户测试 / 验收测试

**做什么**：让实际用户（或你自己以用户身份）试用功能，验证是否达到预期。

**产出文档**：`docs/logs/YYYY-MM-DD-feat-<名>-验收报告.md`

**检查清单**：
- [ ] 对照 Spec 中的成功标准逐项验证
- [ ] 测试正常流程
- [ ] 测试异常流程（输入错误数据、断网等）
- [ ] 测试边界条件（空数据、超长内容等）
- [ ] 记录发现的问题

**此处可能需要你亲自参与**：
- 检查 UI 是否符合预期
- 尝试一些自动测试覆盖不到的交互路径
- 确认功能与你的预期一致

---

### 第 8 步：反馈迭代

**做什么**：根据验收发现的问题，决定下一步。

**三种路径**：
- **发现设计缺陷** → 回到第 2 步，修改 Spec，重新走后续流程
- **发现实现问题** → 回到第 5 步，修改代码
- **有小的改进点** → 创建新 Task 记录，继续完善

**产出文档**：更新 `docs/logs/` 中的对应日志，记录迭代情况。

---

## 范式 B：轻量迭代（Lightweight Iterative）

> **适用场景**：需求简单或模糊，开发过程中逐步明确。
> 典型例子：修改 UI 文案、小的功能调整、修复 Bug。

### 流程总览

```
[1] 需求描述 → [2] 快速设计 → [3] 实现 → [4] 测试 → [5] 验收 → [6] 迭代
```

### 第 1 步：需求描述

简短记录要做什么，50-100 字即可。

**产出文档**：`docs/logs/YYYY-MM-DD-feat-<名>-需求.md`（可简写）

### 第 2 步：快速设计

只写设计要点，不写完整 Spec：
- 要改哪些文件
- 核心变更（几句话说明）
- 注意事项

**产出文档**：在 `docs/logs/` 的同一文档中追加"设计"章节。

### 第 3 步：实现

直接开始编码。遵循增量实现原则，每次改完一个小片段就测试。

### 第 4 步：测试

运行 `go test ./... -race`，确认不破坏现有功能。

**产出文档**：在 `docs/logs/` 中追加"测试"章节。

### 第 5 步：验收

**此处可能需要你亲自参与**。
确认功能符合预期。

### 第 6 步：迭代

根据反馈调整。

---

## 范式 C：实验性探索（Exploratory Prototype）

> **适用场景**：全新的技术方向、不确定能否实现的功能、
> 需要先验证可行性的方案。目标是**快速验证可行性**，
> 不要求代码质量，后续可能重写。

### 流程总览

```
[1] 假设提出 → [2] 最小实验 → [3] 评估结果 → [4] 决策
```

### 第 1 步：假设提出

明确要验证的是什么。例如：
> 假设：DeepSeek API 的 system prompt 可以控制角色扮演风格。

**产出文档**：`docs/logs/YYYY-MM-DD-exp-<实验名>-假设.md`

### 第 2 步：最小实验

用最快的方式验证假设。可以：
- 写一段最小的 Go 程序（甚至不在项目里）
- 用 curl 命令直接调用 API 测试
- 写一个临时的 HTML 页面验证前端方案

**不要求**代码规范、测试覆盖、错误处理。
**要求**：记录实验过程和结果。

### 第 3 步：评估结果

分析实验结果，判断假设是否成立。

**产出文档**：`docs/logs/YYYY-MM-DD-exp-<实验名>-结果.md`

### 第 4 步：决策

- 假设成立 → 用范式 A 或 B 正式实现
- 假设不成立 → 记录原因，归档实验

---

## 范式选择矩阵

| 考量维度 | 范式 A（Spec） | 范式 B（轻量） | 范式 C（实验） |
|---------|:------------:|:------------:|:------------:|
| 需求明确度 | 高 | 中/低 | 低（甚至不确定能否做） |
| 文件改动数 | 5+ | 1-4 | 临时文件 |
| 涉及层级 | 前端+后端+数据 | 单层 | 任意（不保留） |
| 预计工时 | 半天以上 | 1-2 小时 | 0.5-1 小时 |
| 文档要求 | 多 | 少 | 最小 |
| 代码质量要求 | 高 | 中 | 不要求（可丢弃） |
| 需要你参与 | Code Review + 验收 | 验收 | 确认结果 |
| 风险程度 | 中 | 低 | 高（先验证再投入） |

### 快速选择法

```
这条需求需要的工时大概多久？
  ├ < 30 分钟 → 直接改，不需文档
  ├ 30 分 ~ 2 小时 → 范式 B（轻量）
  ├ 2 小时 ~ 1 天 → 范式 A（精简版 Spec）
  └ > 1 天 → 范式 A（完整 Spec）
         └ 不确定能否实现？→ 先用范式 C 验证可行性
```

## Log 日志规范

### 日志存放位置

```
docs/logs/
├── 功能日志/
│   ├── 2026-06-06-feat-ai-角色扮演-需求.md
│   ├── 2026-06-06-feat-ai-角色扮演-实现日志.md
│   ├── 2026-06-06-feat-ai-角色扮演-审查记录.md
│   └── 2026-06-06-feat-ai-角色扮演-验收报告.md
├── 实验日志/
│   ├── 2026-06-06-exp-deepseek-角色扮演-假设.md
│   └── 2026-06-06-exp-deepseek-角色扮演-结果.md
└── 通用日志/
    └── 2026-06-06-项目决策记录.md
```

### 日志文件命名规则

```
YYYY-MM-DD-<类型>-<功能名>-<阶段>.md

类型：
  feat   → 功能开发
  exp    → 实验探索
  chore  → 杂项（依赖升级、配置变更等）

阶段：
  需求       → 需求提出阶段
  设计/方案   → 方案设计阶段
  实现日志   → 编码实现阶段（随 Task 进度追加）
  审查记录   → Code Review 阶段
  验收报告   → 用户验收阶段
  迭代记录   → 反馈迭代阶段
```

### 日志通用模板

```markdown
# 功能开发日志：[功能名称]

- **日期**: YYYY-MM-DD
- **提出人**: [姓名]
- **当前阶段**: [需求提出 / 设计 / 实现 / 审查 / 验收 / 迭代]

---

## 本次记录内容

[记录这个阶段的工作内容、决策、遇到的问题等]

## 决策要点

- 决策 1：[描述]
- 决策 2：[描述]

## 遗留问题

- [ ] 问题 1
- [ ] 问题 2

## 下一步

[明确下一步要做什么]
```

### 日志更新原则

1. **每完成一个阶段就追加或新建日志**
2. **日期要精确到日**（`2026-06-06`）
3. **日志放在 Git 仓库中**，随代码一起提交
4. **日志中引用关键文档**（如 `详见 docs/specs/ai-角色扮演-spec.md`）
5. **决策点要记录理由**（"为什么选 A 不选 B"）
6. **错误也要记录**（"方案 X 尝试后失败，原因是..."）

## 从需求到完成的完整示例（AI 角色扮演功能）

以你提到的"AI 角色扮演功能"为例，展示整个流程怎么走。

### 第 1 步：需求提出 → 写 Log

```markdown
# 功能需求 Log：AI 角色扮演

- **日期**: 2026-06-06
- **提出人**: [你]
- **当前阶段**: 需求提出 ✅

## 功能描述
在 AI 对话面板中，提供一组预设角色（如"专业编辑"、"幽默文案师"、
"严格导师"、"友善读者"），用户选择一个角色后，AI 以该角色的
身份对文档内容进行评价和建议。

## 动机与目标
- 用户可以根据需要获得不同角度的文档反馈
- 增加 AI 功能的趣味性和实用性

## 初步接受标准
- [ ] 有至少 4 个预设角色可选
- [ ] 切换角色后 AI 的回答风格明显不同
- [ ] 角色选择 UI 简洁直观
- [ ] 支持以后再添加新角色
```

### 范式选择

这个功能涉及：
- 后端：修改 AI service 的 system prompt 逻辑
- 前端：新增角色选择 UI
- 改动分布：多层

→ **选择范式 A（Spec-Driven）**

### 第 2 步：编写 Spec

`docs/specs/ai-角色扮演-spec.md`

参考 `12-功能开发流程规范.md · 范式 A · 第 2 步` 的 Spec 模板编写。

### 第 3 步：技术方案设计

`docs/specs/ai-角色扮演-tech-design.md`

**方案对比**：
- **A：后端存储角色列表** — 角色定义保存在 Go 代码中，前端请求时带 role 参数
- **B：前端存储角色列表** — 角色定义在前端，发送请求时附带角色定义到 system prompt

选择方案 A，理由：角色定义在后端，更换角色不需要前端更新，
且便于后续将角色配置化。

### 第 4 步：任务拆解

`docs/specs/ai-角色扮演-tasks.md`

```
Task 1: 后端 — 定义角色数据结构，扩展 AI Service
Task 2: 后端 — 新增 /api/ai/roles 端点返回角色列表
Task 3: 后端 — 修改 ChatStream 接受 role 参数
Task 4: 前端 — 新增角色选择 UI（下拉框/卡片）
Task 5: 前端 — 修改 ai-chat.js 发送 role 参数
Task 6: 测试 — 编写单元测试
```

### 第 5 步：增量实现

按 Task 逐个实现，每个完成后提交 commit。

`docs/logs/2026-06-06-feat-ai-角色扮演-实现日志.md`

### 第 6 步：Code Review

`docs/logs/2026-06-06-feat-ai-角色扮演-审查记录.md`

### 第 7 步：验收

**需要你亲自参与**：试用不同角色，确认对话风格有差异。

`docs/logs/2026-06-06-feat-ai-角色扮演-验收报告.md`

### 第 8 步：迭代

根据你的反馈调整角色定义或 UI。

`docs/logs/2026-06-06-feat-ai-角色扮演-迭代记录.md`
