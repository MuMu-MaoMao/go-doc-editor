# 13 · 范式 Super：特大规模开发流程

> 本文档定义当需求规模极大、涉及多轮范式 A/B/C 时的**顶层编排流程**。
> 范式 Super 本身不直接实现代码，而是将一个超大需求**智能拆解为多个子单元**，
> 每个子单元使用范式 A/B/C 按线性顺序依次完成。

---

## 适用场景

| 特征 | 说明 |
|------|------|
| 需求规模 | 多个模块、多轮迭代，预计总工时 > 3 天 |
| 涉及层级 | 数据库 + 后端 + 前端 + 文档，全栈改动 |
| 关联性 | 子单元之间有前后依赖关系，无法并行开发 |
| 典型例子 | 产品定位转型、数据库架构重构、大规模功能集 |

---

## 流程总览

```
范式 Super：顶层编排
─────────────────────────────────────────────────────────
  Step 1: 全景需求分析    → 产出：全景需求文档（含功能全景图）
  Step 2: 子单元划分      → 产出：子单元划分文档（含依赖关系图）
  Step 3: 全局数据库设计  → 产出：统一数据模型 + 迁移路径
  Step 4~N: 线性执行子单元
      ├── 子单元 1 [范式 A/B/C] → 完成后才能开始子单元 2
      ├── 子单元 2 [范式 A/B/C]
      ├── 子单元 3 [范式 A/B/C]
      └── ...
  最后一步: 全局回归测试  → 产出：全功能验收报告
─────────────────────────────────────────────────────────
```

### 核心原则

1. **先全局设计，后局部实现**
   - 必须先做全景需求分析和全局数据库设计
   - 避免子单元各自为政，导致后期整合冲突

2. **线性执行，不可并行**
   - 子单元必须按依赖顺序一个一个完成
   - 前一个子单元未完成验收，不开始下一个
   - 每个子单元内部按范式 A/B/C 规范执行（留 Log、Code Review、验收）

3. **全局数据模型统一**
   - 所有子单元共享同一份数据库设计
   - 数据库设计在 Step 3 一次性完成，子单元只实现对应的部分

4. **增量演进，不一步到位**
   - 不求第一个版本就完美，核心链路跑通即可
   - 后续通过反馈迭代持续完善

---

## Step 1：全景需求分析

**做什么**：用自然语言描述整个需求的全貌，不涉及技术实现。

**产出**：`docs/specs/<项目名>-全景需求.md`

**检查清单**：
- [ ] 产品定位和目标用户
- [ ] 功能全景图（脑图/列表）
- [ ] 各功能模块的描述
- [ ] 模块之间的关联和依赖
- [ ] 初步的接受标准

## Step 2：子单元划分

**做什么**：根据全景需求，将功能拆分为多个可独立完成的子单元。

**划分原则**：
- 每个子单元是一个完整的范式 A/B/C，独立产出 Spec → 实现 → 验收
- 子单元之间有明确的先后依赖关系
- 每个子单元的预计工时在 1-3 天之间

**产出**：`docs/specs/<项目名>-子单元划分.md`

**检查清单**：
- [ ] 子单元清单（编号、名称、范式类型、预计工时）
- [ ] 依赖关系图（DAG，无循环依赖）
- [ ] 每个子单元的初步范围描述
- [ ] 验收标准：每个子单元的"完成"定义
- [ ] 风险点标注

## Step 3：全局数据库设计

**做什么**：子单元开始之前，一次性设计完整的数据模型。
所有子单元共享这份设计，各自的阶段只实现对应的表和字段。

**产出**：`docs/specs/<项目名>-数据模型设计.md` + ADR

**检查清单**：
- [ ] 所有新表的结构定义（字段、类型、索引、约束）
- [ ] 表与表之间的关系（外键、关联方式）
- [ ] 与现有表的兼容性（是否需要迁移？）
- [ ] 索引策略（查询性能）
- [ ] 数据增长预估和扩展考虑

## Step 4~N：线性执行子单元

**做什么**：按照依赖顺序，逐一执行每个子单元。

每个子单元是一个完整的范式流程：
- **范式 A**：需求提出 → Spec → 技术方案 → 任务拆解 → 增量实现 → Code Review → 验收 → 迭代
- **范式 B**：需求描述 → 快速设计 → 实现 → 测试 → 验收 → 迭代
- **范式 C**：假设提出 → 最小实验 → 评估 → 决策

**关键规则**：
- 子单元之间**不并行**，前一个完成验收后才能开始下一个
- 每个子单元的验收结果记录到全局验收日志中
- 如果发现子单元划分不合理（太大/太小），可以动态调整

## 最后一步：全局回归测试

**做什么**：所有子单元完成后，执行一次全功能回归测试。

**产出**：`docs/logs/YYYY-MM-DD-<项目名>-全局验收报告.md`

**检查清单**：
- [ ] 对照全景需求的接受标准逐项验证
- [ ] 所有子单元之间的接口是否正常联动
- [ ] 全局数据一致性检查
- [ ] 性能基线是否在可接受范围
- [ ] 文档（readme、API 文档）已全部更新

---

## 范式 Super 与范式 A/B/C 的关系

```
范式 Super（顶层编排）
│
├── Step 1: 全景需求分析
├── Step 2: 子单元划分
├── Step 3: 全局数据库设计
│
├── Step 4: 子单元 1 ─── 范式 A（完整规格）
│   ├── 需求提出 → Spec → 方案设计 → 任务拆解 → 实现 → 审查 → 验收 → 迭代
│   └── 产出：Log + 代码 + 测试
│
├── Step 5: 子单元 2 ─── 范式 A/B（视规模而定）
│   └── ...
│
├── Step 6: 子单元 3 ─── 范式 B（轻量迭代）
│   └── ...
│
└── 最后一步: 全局回归测试
```

### 范式选择的维度

| 子单元特征 | 推荐范式 |
|-----------|---------|
| 涉及多层（数据库+后端+前端），文件数 5+ | **范式 A** |
| 单层改动，文件数 1-4 | **范式 B** |
| 技术方向不确定，需要先验证 | **范式 C** |
