# ADR-002: AI 后端代理架构决策

- **状态**: Accepted
- **提出日期**: 2026-05-15
- **提出人**: 项目初始团队

## 上下文

需要为文档编辑器增加 AI 对话功能，用户可以在编辑器中向 AI 提问
（如润色、翻译、总结文档内容）。关键约束：

- AI API 密钥不能暴露在前端（前端静态文件可被直接查看）
- 需要流式响应（用户体验好）
- 当前选择的 AI 模型为 DeepSeek-Flash（性价比高）

## 考虑的方案

### 方案 A：纯前端调用（直接调用 DeepSeek API）
- 优点：后端改动最小
- 缺点：API 密钥暴露在前端代码中，严重安全风险
- 结论：❌ 安全性不可接受

### 方案 B：后端代理模式（选中）
- 优点：API 密钥保存在后端；后端可做额外的安全校验（JWT）
- 缺点：增加后端开发量
- 成本：新增 2 个后端文件 + 1 个前端文件 + 修改 3 个后端文件

### 方案 C：WebSocket 全双工通信
- 优点：真正的双向实时通信
- 缺点：SSE 已满足需求，WebSocket 增加了连接管理复杂度
- 成本：需要 WebSocket 连接管理，架构更复杂

## 决策

选中**方案 B（后端代理模式）**，理由：

1. API 密钥安全得到保障（仅后端持有）
2. SSE（Server-Sent Events）协议简单可靠，适合单向流式推送
3. JWT 认证可无缝融入现有中间件体系

## 影响

### 正面影响
- API 密钥不暴露在前端
- AI 请求链路清晰：前端 → 后端 → DeepSeek API → 后端 → 前端 SSE
- 更换 AI 模型时只需修改后端

### 负面影响
- 所有 AI 流量都经过后端，增加后端带宽消耗
- 流式响应依赖 `http.Flusher`，不能在所有部署环境下工作
