# ADR-005: 文档存储从文件系统迁移至 MySQL 数据库

- **状态**: Accepted
- **提出日期**: 2026-06-06
- **提出人**: [用户]

---

## 上下文

项目最初的文档存储使用文件系统（`C:\doxreader/{username}/`），每次文件操作直接读写磁盘文件。
随着功能增加（用户认证、AI 对话、数据库存储），文档数据成为唯一游离在数据库之外的数据，
导致以下问题：

1. **数据分散**：用户数据（users 表）和文档数据（文件系统）分开存储，备份/迁移需要额外处理
2. **元数据缺失**：文件系统无法追踪文档的创建时间、更新时间、版本等信息
3. **查询能力有限**：不支持按内容搜索、按时间排序等数据库原生能力
4. **路径依赖问题**：Windows 路径硬编码，跨平台部署需要额外适配
5. **安全维护成本**：手动实现路径遍历防护（`safeFilePath`），数据库存储天然安全

现在项目已全面使用 MySQL（users + login_logs + ai_keys 三张表），将文档也迁移到数据库
的时机已经成熟。

---

## 考虑的方案

### 方案 A：新增 docstore 包 + FileService 委托（选定）

**描述**：
- 新增 `internal/docstore/` 包，封装文档 CRUD 的 SQL 操作
- `FileService` 修改构造函数，接收 `*docstore.Store`，方法内部委托给 store
- 数据表 `documents`：id / username / filename / content / created_at / updated_at
- 使用 `INSERT … ON DUPLICATE KEY UPDATE` 实现 upsert 语义

优点：
- 与 `user.Store` 模式一致，架构风格统一
- handler 层零改动，降低风险
- 关注点分离：存储逻辑独立成包
- 可测试性：docstore 可独立测试
- 可扩展：未来可增加版本管理、全文搜索

缺点：
- 多一个包需要维护
- 现有文件系统上的历史文档不自动迁移

成本：新增 1 文件 + 修改 4 文件，约 2-3 小时工时

### 方案 B：直接在 FileService 中使用 *sql.DB

**描述**：
- 不新增独立包，FileService 直接持有 `*sql.DB`
- 所有 SQL 直接在 `file_service.go` 中书写

优点：
- 改动最少，只改 1 个文件

缺点：
- 违反单一职责：FileService 同时处理业务逻辑和数据访问
- 与 `user.Store` 模式不一致，架构不统一
- 难以独立测试数据库逻辑
- 业务逻辑和 SQL 混杂，不利于维护

### 方案 C：移除 FileService，handler 直接操作数据库

**描述**：
- 删除 `file_service.go`，handler 直接调用 docstore
- 省略业务逻辑层

优点：
- 减少一层抽象

缺点：
- 打破现有分层架构
- handler 职责膨胀
- 未来添加业务逻辑（如文件大小校验、格式检查）没有合适位置

---

## 决策

选定 **方案 A**：新增 `docstore` 包 + FileService 委托。

理由：
1. **架构一致性**：与 `user.Store` 保持相同模式，数据库操作独立成 store
2. **最小风险**：handler 层和前端完全不变，API 接口向后兼容
3. **长期维护**：关注点分离，docstore 可独立演进
4. **团队一致性**：同一项目中两种数据存储（user / doc）采用同一种模式，降低认知负担

---

## 影响

### 正面影响
- 文档数据纳入 MySQL 管理体系，统一备份和迁移
- 可追踪文档的创建时间和最后更新时间
- 为后续功能（全文搜索、文档版本管理、标签系统）奠定基础
- 移除路径遍历安全隐患
- 项目不再依赖特定文件系统路径

### 负面影响
- 现有文件系统上的文档不会自动迁移到数据库（本次不提供迁移脚本）
- 新增一个包文件，项目结构略微扩大

### 迁移注意事项
- 配置文件中的 `storage` 字段暂时保留（标记为可选），不破坏现有 `config.json`
- 启动项目时不再检查 `storage` 目录是否存在
