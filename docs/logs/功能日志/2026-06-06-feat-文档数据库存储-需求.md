## 功能描述

将文档的存储方式从**文件系统**（目前存储在 `C:\doxreader/{username}/` 目录下）迁移到 **MySQL 数据库**中。前端逻辑基本保持不变（API 接口格式不变、UI 交互不变），主要是后端的文档数据读写路径改为数据库操作。

具体来说，当前文件系统的操作：
- 文件列表：`os.ReadDir(用户目录)`
- 文件读取：`os.ReadFile(文件路径)`
- 文件保存：`os.WriteFile(文件路径, 内容)`
- 文件删除：`os.Remove(文件路径)`

将全部替换为对应的数据库 CRUD 操作，新增一张`文档表`来存储文档数据。

## 动机与目标

- **解决什么问题**：当前文件系统存储存在以下问题
  - 数据分散在文件系统，备份/迁移需要额外处理文件
  - 文档元数据（创建时间、更新时间、文件大小等）无法追踪
  - 无法利用数据库的查询能力（如模糊搜索、排序等）
  - 文件路径依赖操作系统，在 Windows 上硬编码 `C:\doxreader`，部署时容易出问题

- **目标用户**：所有使用该文档编辑器的用户（后端迁移对前端用户透明）

- **不做这个功能的代价**：功能越加越多，但文档数据却游离在数据库之外，数据一致性难以保证；后续想做全文搜索、文档版本管理等功能，都需要文档数据已在数据库中

## 初步接受标准

- [ ] 新增 `documents` 表（或类似名称），包含至少：id、用户名、文件名、内容、创建时间、更新时间
- [ ] 数据库表有合适的索引（用户名索引、用户名+文件名唯一索引）
- [ ] 后端文件 CRUD 全部走数据库，不再依赖文件系统存储目录
- [ ] 前端 API 接口（`GET /api/files`、`GET /api/file/{name}`、`POST /api/file/{name}`、`DELETE /api/file/{name}`）的请求/响应格式**保持不变**
- [ ] 文件 Service 层行为不变（同一个 API 接口返回同样的 JSON 结构）
- [ ] 项目能正常启动，不依赖 `storage` 配置项指向的目录存在
- [ ] 所有现有功能（注册、登录、AI 对话、用户主页）不受影响

|------|------|------|
| **A ✓** | 新增 docstore 包 + FileService 委托 | **选中** |

### 数据表结构（documents）

| 字段 | 类型 | 说明 |
|------|------|------|
| id | BIGINT AUTO_INCREMENT | 主键 |
| username | VARCHAR(255) | 所属用户 |
| filename | VARCHAR(255) | 文件名 |
| content | LONGTEXT | 文档内容 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 最后更新时间（ON UPDATE） |

唯一索引：`(username, filename)` — 同一用户下文件名唯一

### 安全审计

- SQL 注入：全部参数化查询
- 用户隔离：所有查询 WHERE 包含 username
- 路径穿越：不再需要，数据库存储天然免疫
- 所有 handler 层接口不变，前端不变
